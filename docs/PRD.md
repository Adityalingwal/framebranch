# FrameBranch — Project Requirements Document

## Overview

Code has Git. A programmer can create a separate branch, edit it independently, see exactly what changed, and merge it back together with everyone else's work.

Video has nothing like this. A shared video project is usually one file, saved over and over, with editors relying on filenames like "final_v3_actual.mp4" to keep track of versions. Two editors working on the same project at the same time have no real way to work independently and then bring their work back together — one person's changes simply overwrite the other's.

The reason video hasn't gotten something like this isn't lack of need — it's that the ideas from code don't transfer directly. A code change is a few edited lines, and a conflict is two edits touching the same line. A video edit is a different shape entirely — trimming a clip, moving it, changing its volume — and it isn't obvious what "the difference between two versions" should even look like on a timeline, or how to show two conflicting edits to a person in a way they can resolve without first learning how Git works.

FrameBranch is a version-control system built specifically for video timelines. It lets an editor create a separate line of work, make edits there independently, see precisely what changed compared to the original, and combine two sets of changes into one — automatically wherever the edits don't overlap, and with a clear one-click choice wherever they do, no Git knowledge required.

## Scope

FrameBranch is built for a person working with an agent on a single video project. There is no multi-user collaboration system in this version — supporting more than two participants at once is a separate problem from version control, and it's out of scope here.

This is a starting-phase scope choice: the demo specifically uses a person and an agent because that matches the actual problem this project solves. With a small amount of additional code, the same underlying system could support two people collaborating instead of a person and an agent — the branching and merging mechanics don't change either way. Multi-user collaboration wasn't included because it isn't needed for this starting phase and would add complexity without adding to the core problem being solved.

The agent's edits are simulated rather than generated by a real AI model: a "Simulate agent edits" button applies a fixed, scripted set of edits to a branch, tagged as coming from the agent rather than the person. This is a deliberate scope decision, not a shortcut around a hard problem — FrameBranch exists to solve the version-control problem (branching, diffing, merging, resolving conflicts for video), not to build an AI video-editing agent. Cardboard already has AI-driven editing; wiring in a real AI agent here would be solving a different problem than the one this project is about. Every edit already carries a record of who made it, so plugging in a real agent later needs no change to the version-control system itself.

## Operations

FrameBranch supports eight operations on a video timeline in version 1:

- Add a clip
- Delete a clip
- Move a clip
- Trim a clip (shorten or extend it from its start or end)
- Slip a clip (keep its position and length, but shift which part of the source file it shows)
- Split a clip into two
- Change a property — limited to six: volume, opacity, scale, position, text content, and text style
- Ripple delete (delete a clip and shift everything after it on that track left, to close the gap)

Each operation has to work the same way in five places: the edit itself, undoing it, comparing two versions, merging two versions, and detecting a conflict when both versions used it on the same clip. Adding an operation is expensive in that sense, so version 1 keeps this list to the smallest set that can run a real editing demo.

Five operations were left out of version 1:

- **Transitions** (like a crossfade between two clips) — the boundary between two clips is complicated to represent and merge.
- **Named effects** (blur, color grading, and similar) — the "change a property" operation already covers this for the six chosen properties.
- **Reordering tracks.**
- **A separate operation for captions** — captions are text clips on a text track, so they already use the same eight operations as any other clip.
- **A direct "change the timeline range" operation** — moving and trimming already cover every way a clip's position and length can change.

Splitting a clip is the riskiest of the eight. It raises a question code version control doesn't have: when a clip splits into two, which piece is "the original," for later edits and merges.

## Conflict UX

A conflict happens when both branches make edits that can't be combined automatically. FrameBranch shows every conflict as a side-by-side comparison: the original clip, the person's version, and the agent's version, laid out as bars next to each other, with a one-line plain-English explanation of what each side changed (for example, "Volume changed to 40 on your side, 70 on the agent's side").

Two other ways to show a conflict were considered and rejected. Showing only text, with no visual comparison, doesn't let someone resolve a conflict without understanding how the underlying system works — video edits need to be seen, not just described. A live preview with drag-to-adjust controls was rejected too: it turns the conflict screen into a second editor, which is its own large project outside version 1's scope.

Every conflict falls into one of three types, and each type gets its own fixed set of one-click buttons — resolving a conflict never requires typing or manual input:

1. **Same thing, two different values** — both sides changed the same property of the same clip (for example, both changed its volume, to different numbers). Buttons: Keep your version, Keep the agent's version, Keep the original.
2. **Delete versus anything** — one side deleted a clip, the other side edited it. Buttons: Keep the delete, Keep the clip, Keep the original.
3. **Neither edit is a problem alone, but together they create one** — the person makes one change, the agent makes a separate change, and each is fine by itself. The problem only shows up once both are combined.

   Example: the person moves clip A to a new spot on the timeline. Separately, the agent makes clip B longer. It happens that B's new, longer length now reaches into the exact spot where A was moved — A and B now overlap, even though neither edit was made with the other in mind.

   Three buttons resolve it:
   - **Shift A** — keep B's new length, and automatically move A to the next open gap instead.
   - **Shift B** — keep A's new position, and automatically move B to the next open gap instead.
   - **Undo both, back to the original** — cancel both edits; neither the move nor the length change happens.

These three types cover every possible conflict between the eight operations — there's no fourth kind of clash version 1 doesn't have a button for.

## Non-goals

Version 1 solves one specific problem — version control for a video timeline. The following are explicitly not part of it:

- **Real-time collaboration** — multiple people editing the same timeline live, seeing each other's changes as they happen. FrameBranch works through branches that are combined afterward, not live shared editing.
- **Multi-user accounts and permissions** (see Scope) — built for one person and one agent, no login system.
- **Versioning the video files themselves** — FrameBranch tracks a pointer to each media file and a fingerprint to detect if the file changed, not the actual bytes inside it. Editing a video file's content (like re-encoding it) is outside this system.
- **A real AI editing agent** (see Scope) — the agent's edits are scripted for this version.
- **Direct integration into another product's codebase** — FrameBranch connects only through OTIO import and export files, as a standalone system.
- **Full timeline playback** — clips can be previewed one at a time; playing the whole timeline back as one continuous video is not built.
- **Transitions, named effects, and track reordering** (see Operations).
- **A full video editor** — FrameBranch is a version-control layer that sits on top of an editing workflow, not a replacement for one.
- **Rendering a final video file** — export produces an OTIO file (a project format), not an .mp4.
- **A UI built for large-scale timelines** — the underlying engine is tested and measured at 10,000 clips; the interface itself is built and polished for a demo-sized timeline (10 to 30 clips).

## Demo Story

The demo walks through the full system in nine steps, using a single project:

1. **Import** — a video project is imported from an OTIO file (the format used to exchange project files between editing tools).
2. **Branch** — a new branch is created and switched to, so edits from here on happen on a separate line of work instead of the main one.
3. **Person edits** — the person makes a few edits directly on the timeline (for example, changing a clip's volume).
4. **Agent edits** — the simulated agent runs its own separate, scripted set of edits.
5. **Diff** — the two versions are compared, and every change is shown as a plain-English line (for example, "Volume changed from 50 to 80").
6. **Merge** — the two branches are combined into one.
7. **Resolve conflicts** — every conflict the merge produces is shown on screen, each one of the three types described earlier, with its own one-click buttons.
8. **History** — the project's history shows every edit, marked with who made it — the person or the agent — including the merge itself, which shows both branches it came from. An earlier version can be restored from here.
9. **Export** — the project exports to an OTIO file (a project format), not a rendered video file.

## Known Limitations

These are not bugs — everything below still works correctly. The data is always right; the UI just doesn't show or remember all of it yet:

- **No visual preview of the original clip in a conflict.** The conflict screen shows "Yours" and "Agent's" versions side by side; the original ("Base") is a placeholder labelled "not available to preview." Choosing "Keep the original" still restores the correct data — you just can't see it before choosing.
- **Branch tracking resets on a hard browser reload.** Which branch is active, and the list of known branches, are held in browser memory, not fetched from the server. A hard reload clears them from the UI (you fall back to manual pickers); nothing is lost in the database.
- **Clips don't have their own name.** A clip's label in the timeline is derived from its source media filename. Two clips that use different trims of the same file will show the same label and aren't visually distinguishable.
